# Коммиты, push и релизы

[English](git-workflow.md) · [Участие в разработке](../CONTRIBUTING.ru.md) · [Инструкции проекта](../AGENTS.md)

Прочитайте руководство перед созданием коммита, push или подготовкой релиза. Оно задаёт порядок работы, но не разрешает публикацию само по себе. Следуйте последнему указанию пользователя о коммитах, push, ветке и релизе. Запрос на функцию сам по себе не разрешает коммит или push.

## Формат коммита

Используйте Conventional Commits. Всё сообщение пишется на английском:

```text
<type>[optional scope][optional !]: <description>

<Brief problem or user need and resulting behavior.>

- <Meaningful change>
- <Important compatibility detail or edge case>

Validation: <checks actually performed and results>.
Limitations: <significant unverified behavior, when relevant>.

BREAKING CHANGE: <incompatible behavior and migration, when applicable>
```

Тело, список и ограничения необязательны, когда в них нет необходимости. Для небольшой правки достаточно заголовка и абзаца о проверке. Для существенного изменения объясните проблему и результат в одном-двух предложениях, сгруппируйте изменения в список и завершите реальными проверками и значимыми ограничениями. Блок о нарушении совместимости нужен только при несовместимом изменении.

### Типы

| Тип        | Назначение                                                 |
| ---------- | ---------------------------------------------------------- |
| `feat`     | Новая пользовательская возможность или поведение           |
| `fix`      | Исправление неверного поведения                            |
| `perf`     | Улучшение производительности                               |
| `refactor` | Перестройка реализации без изменения поведения             |
| `docs`     | Документация или снимки для неё                            |
| `style`    | Только форматирование кода, не дизайн интерфейса           |
| `test`     | Тесты или тестовая инфраструктура без изменений приложения |
| `build`    | Настройки сборки, упаковка или зависимости                 |
| `ci`       | CI-процессы и их настройки                                 |
| `chore`    | Обслуживание, не подходящее под остальные типы             |
| `revert`   | Отмена прежнего коммита; укажите его в теле                |

Выбирайте тип по основному результату. Тесты и документация, поддерживающие функцию, входят в её коммит `feat` или `fix`. Для ошибки упаковки используйте `fix`; для изменения системы сборки без исправления ошибки — `build`. Подготовка релиза обозначается `chore(release)`.

### Область и описание

Область необязательна. Используйте короткую устойчивую область: `editor`, `reading`, `workspace`, `attachments`, `vault`, `graph`, `canvas`, `settings`, `appearance`, `i18n` или `release`. Если изменение затрагивает несколько областей, область можно опустить; не придумывайте длинные составные названия.

Описание начинается с английского глагола в повелительной форме со строчной буквы: `add`, `fix`, `preserve`, `remove`, `refresh` или `document`. Желательная длина всего заголовка — до 72 символов, без точки в конце. Описывайте итоговый результат, а не имена файлов, брошенные подходы или историю обсуждения. Избегайте расплывчатых заголовков вроде `fix stuff` и `various improvements`.

```text
feat(editor): add heading folding
fix(attachments): map insertion positions through edits
feat(appearance): add graphite themes and Constellation branding
docs: refresh bilingual screenshots
ci: verify release artifacts before upload
chore(release): prepare Aether 1.2.2
```

При нарушении совместимости используйте `!` и отдельный блок `BREAKING CHANGE:`, объяснив, кого затронет изменение и как перейти на новое поведение. Внутренний рефакторинг и обычное исправление ошибки не становятся несовместимыми автоматически. Пример:

```text
feat(api)!: require revision tokens when saving notes

Reject saves without an expected revision to prevent stale writes.

BREAKING CHANGE: API callers must supply the last-read revision token.
```

Примеры показывают формат и не утверждают, что такая работа выполнена. Conventional Commits сами по себе не создают changelog, не выбирают версии и не публикуют релизы: такая автоматизация здесь не настроена.

## Перед коммитом и push

1. Проверьте ветку, upstream, remote, рабочее дерево и полный diff. Сохраните посторонние изменения и пользовательские файлы. Один коммит должен давать один связный результат.
2. Выполните проверки по масштабу изменения согласно [руководству разработчика](../CONTRIBUTING.ru.md). Для документации обычно достаточно форматирования, вычитки и проверки ссылок. Исправьте внесённые ошибки, остальные опишите честно.
3. Добавьте в индекс только запрошенную работу. Просмотрите пути и staged diff, выполните `git diff --cached --check`. Проверьте ignore-правила, отслеживаемые и неотслеживаемые файлы. Не добавляйте личные или сгенерированные данные принудительно.
4. Исключите личные хранилища, профили, секреты, базы, кэши, программы и установщики. `vault/` — исключение для синтетического демонстрационного хранилища; локальные добавления в него не разрешены к публикации автоматически. Если личные данные уже отслеживаются или закоммичены, остановите публикацию и объясните ситуацию; не удаляйте данные и не переписывайте историю молча.
5. Для многострочного сообщения используйте файл или структурированный аргумент. Указывайте только реальные проверки, различая unit-тесты, сборку, целевые нативные сценарии и ручной осмотр. Числа берите из результатов запуска. Успешная сборка не доказывает правильность работы приложения.
6. После коммита проверьте его содержимое и состояние рабочего дерева. Перед разрешённым push просмотрите все исходящие коммиты на личные и сгенерированные файлы. После push проверьте целевую удалённую ветку и сообщите коммит и назначение.

Не изменяйте опубликованные коммиты, не делайте force-push и не переписывайте общую историю без прямого запроса. Не удаляйте и не включайте посторонние изменения молча.

## Формат релиза и обязательные файлы

Используйте [двуязычный шаблон релиза](release-template.md), основанный на [Aether 1.2.1](https://github.com/d0rsett/aether/releases/tag/v1.2.1). Сохраняйте порядок и заголовки: `## Aether <версия> — <английское название>`, список изменений, `### Downloads`, `### Verification`, ссылки на проверки/сборки/коммит, затем `## По-русски`, соответствующий список изменений, сведения о загрузках и проверках. Сначала полностью завершите английский блок, затем русский. Не чередуйте языки и не заменяйте разделы другой структурой.

Заменяйте каждый заполнитель реальными сведениями о текущем релизе. Добавляйте или убирайте пункты изменений по фактическому объёму, сохраняя смысл и порядок в обоих языках. Переводите сведения о загрузках и проверках, а не только изменения. Указывайте реальные проверки и ограничения; не копируйте прежние числа тестов, ссылки CI, сведения о подписи и доступных платформах без проверки. При изменении поддержки платформ или подписи обновите соответствующие утверждения шаблона. Шаблон не включает автоматическую публикацию релизов.

Обычный релиз должен содержать установщик и портативную версию для каждой релизной платформы, а также контрольные суммы:

| Платформа                               | Дистрибутив                  | Файл                                                      |
| --------------------------------------- | ---------------------------- | --------------------------------------------------------- |
| Windows x64                             | Установщик NSIS              | `Aether_<version>_x64-setup.exe`                          |
| Windows x64                             | Портативный исполняемый файл | `Aether_<version>_Windows_x64.exe`                        |
| macOS universal (Intel + Apple Silicon) | Установочный образ DMG       | `Aether_<version>_universal.dmg`                          |
| macOS universal (Intel + Apple Silicon) | Портативный архив приложения | `Aether-macos-universal.app.zip`, содержащий `Aether.app` |
| Все четыре загрузки                     | Контрольные суммы SHA-256    | `SHA256SUMS.txt`                                          |

`.github/workflows/release.yml` собирает Windows с `--bundles nsis -- --locked`, macOS — с `--target universal-apple-darwin --bundles app,dmg -- --locked`. Затем копирует исполняемый файл той же Windows-сборки в портативный файл с версией и архивирует приложение той же macOS-сборки через `ditto --keepParent`. Скачивайте оба артефакта: `aether-windows-x64` и `aether-macos-universal`. Все четыре дистрибутива должны происходить из окончательного коммита релиза; не подменяйте их тестовыми сборками или файлами другой версии. После сбора четырёх файлов создайте и приложите манифест контрольных сумм.

Не публикуйте молча релиз только с установщиком, только с портативной версией или только для одной платформы. Если обязательный файл не собрался, исправьте и пересоберите его до публикации, если пользователь прямо не изменил состав релиза. Отличайте успешную сборку для платформы от проверки работы приложения на ней.

## Подготовка релиза

1. Проверьте разрешение на релиз, итоговый объём, версию, ветку и remote. Изучите существующие теги и релизы; не заменяйте опубликованный релиз и не перемещайте его тег без прямого разрешения.
2. Согласованно обновите пакет и lockfile фронтенда, версию Tauri, Cargo manifest и lockfile хоста. Обновите обе истории изменений, версии и ссылки README, затронутые руководства на русском и английском. Указывайте версию в заголовке коммита только там, где она относится к подготовке релиза.
3. Для новых снимков используйте изолированные синтетические хранилища из [нативных проверок](native-testing.ru.md). Осмотрите каждый снимок на личные пути, папки, имена, подсказки и диалоги. Не снимайте обычный профиль или личное хранилище пользователя.
4. Выполните подходящие проверки и соберите обычные артефакты без `e2e`. Сохраните запущенное приложение; при занятом файле используйте другую папку Cargo target. Для нативной интеграции подготовьте соответствующую тестовую сборку и выполните затронутые изолированные сценарии. Проверьте форматы значков по [визуальному оформлению](branding.ru.md).
5. Закоммитьте и отправьте только разрешённые исходники и документацию. Запускайте `.github/workflows/release.yml` с полным SHA окончательного коммита: checkout не распознаёт сокращённый SHA как коммит. Дождитесь проверок и сборок запрошенных платформ, исправьте ошибки. Не подменяйте их программами старой версии и не называйте незавершённые сборки успешными.
6. Подготовьте черновик релиза для точного итогового коммита по `docs/release-template.md`: сначала английский блок, затем русский. Скачайте успешные артефакты, по возможности проверьте версии, архитектуры и значки, приложите все четыре обязательных дистрибутива. Точно опишите загрузки, требования WebView2, наличие подписи и нотарификации, выполненные проверки и ограничения проверки работы приложения.
7. Создайте `SHA256SUMS.txt` с именами файлов без локальных путей. Сверьте размеры и суммы загруженных файлов с локальными. Держите сборки во вложениях релиза, вне Git.
8. Опубликуйте разрешённый релиз после готовности файлов и проверок. Проверьте публичную страницу, целевой коммит тега, нужный статус Latest/prerelease и вложения. Сообщите ссылку, отправленный коммит, проверки и значимые ограничения.
